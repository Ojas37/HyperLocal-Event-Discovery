# REPLIT AGENT MASTER PROMPT — LOCALLOOP

## 1. Your Role and Mission

Act as a senior full-stack software engineer, UI/UX designer, product architect, database engineer, and QA specialist.

Build a complete, production-minded, responsive web application named **LocalLoop — Hyperlocal Event Discovery & Community Engagement Platform**.

This application solves the problem of fragmented event discovery. Hackathons, workshops, tech meetups, conferences, startup events, college festivals, networking sessions, and community gatherings are scattered across WhatsApp, Instagram, LinkedIn, posters, and individual websites.

LocalLoop brings these events together in one place and helps users discover relevant nearby events, register for them, attend them, and remain connected with organizers.

**Core product loop:**
Discover → RSVP → Attend → Connect → Rediscover.

Do not create only a static UI, landing page, or frontend prototype. Build a functional full-stack application with real navigation, persistent data, authentication, forms, search, filtering, role-based dashboards, and working event workflows.

Prioritize a polished MVP that works reliably, while organizing the architecture so advanced features can be added later.

## 2. Product Identity and Branding

**Product name:** LocalLoop

**Tagline:** Find Your People. Discover Your Next Thing.

**Product category:** Hyperlocal Event Discovery & Community Engagement.

**Target users:**
- College students searching for hackathons, workshops, internships, and networking opportunities.
- Early-career professionals looking for tech meetups, conferences, and skill-building sessions.
- Event organizers, college clubs, startups, companies, and communities.
- Administrators responsible for event moderation and platform quality.

**Brand personality:** Modern, trustworthy, energetic, community-driven, intelligent, and professional.

The product should feel like a premium startup application that could be presented to hackathon judges, investors, colleges, and real users.

## 14. Database Design

Create a normalized PostgreSQL schema with migrations and appropriate indexes.

Include these core tables or equivalent entities:

1. `users`
   - ID, name, email, password hash or provider identity, avatar, role, institution, preferences, privacy settings, timestamps.

2. `organizers`
   - ID, owner user ID, name, type, description, logo, website, verification status, timestamps.

3. `organizer_members`
   - Organizer ID, user ID, role, permissions.

4. `events`
   - ID, organizer ID, title, slug, description, category, tags, banner, start/end times, timezone, venue, address, coordinates, mode, price, capacity, registration deadline, external URL, status, created/updated timestamps.

5. `rsvps`
   - ID, user ID, event ID, status, registration answers, QR token reference, timestamps.

6. `check_ins`
   - ID, RSVP ID, check-in time, method, staff user ID.

7. `saved_events`
   - User ID, event ID, creation time.

8. `organizer_follows`
   - User ID, organizer ID, creation time.

9. `communities`
   - ID, organizer ID where applicable, name, description, image, location, topics.

10. `community_members`
    - User ID, community ID, membership status.

11. `event_reviews`
    - User ID, event ID, rating, feedback, timestamps.

12. `notifications`
    - User ID, type, title, message, read status, target URL, timestamp.

13. `event_reports`
    - User ID, event ID, reason, description, status, resolution, timestamps.

14. `organizer_verification_requests`
    - Organizer ID, submitted details, status, reviewer, timestamps.

15. `user_badges`
    - User ID, badge type, earned timestamp.

16. `analytics_events`
    - Event ID, actor where appropriate, action type, timestamp, minimal relevant metadata.

17. `audit_logs`
    - Actor ID, action, target, timestamp, and appropriate metadata.

Add database constraints, foreign keys, uniqueness rules, and indexes for event dates, categories, organizer IDs, registration status, and geographic lookups where supported.

Enforce one RSVP per user per event and one check-in per registration.

Use database transactions for capacity checks, waitlists, and seat allocation to prevent overbooking.

Store timestamps consistently and render them in the appropriate timezone.

Never store plaintext passwords or unnecessary precise location history.

## 16. Location and Recommendation Logic

Implement useful geographic discovery without requiring a paid API.

Use coordinates when available. Calculate distance with a standard geographic distance formula or PostGIS if supported.

When the user has not granted location permission:
- Use the manually selected area.
- Allow location filtering by city or area.
- Continue to show useful general results.

Do not fabricate travel times or precise distances when coordinates are unavailable.

Use an explainable weighted ranking model, for example:

- Interest match: 35%.
- Geographic proximity: 25%.
- Date and schedule relevance: 15%.
- Organizer quality: 10%.
- Popularity: 10%.
- Freshness and registration urgency: 5%.

Treat these weights as initial configurable defaults, not validated performance claims.

Normalize features to comparable scales. Filter out cancelled and expired events by default. Use diversity rules so that the feed does not show only one category.

For a new user, use onboarding interests and popular events from the selected area. If no events exist in that area, show a helpful empty state and offer nearby or broader search.
